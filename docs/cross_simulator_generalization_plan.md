# Proposed cross-simulator generalization study

Planning draft, October 26, 2026. No second simulator has been installed or
evaluated as part of this proposal. Existing frozen experiments are unchanged.
For current behavior, see [simulation_pipeline.md](simulation_pipeline.md).

## Question and primary comparison

Does the benefit of targeted observation-condition randomization persist
when test images are generated by an independently implemented simulation
pipeline, and how does that benefit change under additional source/observation
shifts?

Freeze the existing standard-trained and randomized three-seed CNN ensembles.
Evaluate both on exactly the same new parents in each test domain, using each
checkpoint's existing normalization. The initial experiment is zero-shot:
no target-domain training, fine-tuning, or recomputation of image statistics.

This separates two questions that should not be pooled:

1. **Implementation transfer:** do equivalent physical and observation models
   rendered by different software give consistent estimates?
2. **Modeling-assumption transfer:** does the improvement survive different
   source structure, PSF shape, noise behavior, or parent populations?

Equivalent correct implementations may produce almost identical images.
That is a useful control, but not evidence of broad domain robustness. A new
software package is also not automatically more physically realistic.

## Candidate backend and compatibility gate

Use **PyAutoLens as the first candidate**, subject to an installation and API
compatibility audit in a separate pinned environment. Its documented
`SimulatorImaging` API supports strong-lens image formation with PSF and
noise. This is a candidate choice, not an implemented integration.

Primary references:

- [PyAutoLens simulation API](https://pyautolens.readthedocs.io/en/latest/api/_autosummary/autolens.SimulatorImaging.html).
- [PyAutoLens introductory workflow](https://pyautolens.readthedocs.io/en/latest/overview/overview_1_start_here.html).

Audit point-source support before choosing this backend for the existing
extended-plus-point-source scenes. If it cannot reproduce that scene through
its supported API in the available time, record the limitation. Do not silently
remove point sources and describe the resulting difference as software alone.
Prefer a supported alternative or explicitly define a separate morphology
shift experiment. Share manifests and physical specifications where useful;
record any shared source, PSF, detector, or processing code.

## Phase 1: agree on the physical target and image contract

Create a backend-neutral scene specification, including mass family, target
definition, axis ratio, orientation, centers, source light, point-source
amplitude, angular units, detector units, pixel geometry, and observation state.

Check conventions rather than copying equal numeric parameter values:

- `(x, y)` versus `(y, x)`, orientation handedness, and array flips.
- Ellipticity parameterization and major-axis angle.
- SIE normalization and the precise meaning of Einstein radius.
- Sersic effective-radius and amplitude definitions; match physical light or
  integrated flux after establishing each backend's definitions.
- Pixel-integrated flux versus sampled surface brightness, including pixel area.
- Point-image locations, flux, PSF centering/normalization, and convolution edges.
- Exposure, background, photon noise, read noise, and output rate units.

If necessary, implement a derived common physical radius and validate the
mapping to the existing CNN target before scoring. For a different mass
family, equal raw parameter names need not denote equal quantities; keep
mass-family shifts out of the first experiment.

Use analytic SIS cases, then matched elliptical SIE cases. On development
parents only, compare deflection fields, image positions, noiseless images,
integrated flux, PSF impulse responses, and repeated-noise mean/variance.
Freeze quantitative acceptance tolerances after a numerical convergence
study and before final model scoring. Do not require different random-number
implementations to produce identical noisy pixels.

**Deliverable:** a convention mapping, component-sharing matrix, and passed
control report. If controls fail, the result is an integration problem until
the difference is understood.

## Phase 2: define test domains separately

| Domain | What changes | Interpretation |
|---|---|---|
| A: new original-backend control | New parents, original rendering and proposal | Checks current performance on a fresh sample. |
| B: matched alternate backend | Same new physical parents and observation specification, independently rendered | Measures implementation transfer after convention alignment. |
| C: alternate backend with a new PSF family | Domain B plus one independently specified non-Gaussian PSF treatment | Tests a new observation-model assumption. |
| D: alternate backend with source-structure shift | Domain B plus a validated richer source representation | Tests morphology transfer. |
| E: new nuisance combinations or ranges | Separately fixed combinations/intermediate values, then optionally out-of-range values | Distinguishes joint-condition and range generalization. |

For a one-month project, prioritize A, B, and **one** well-validated shift from
C or D. Do not combine every difference into one unexplained target dataset.
The alternate backend should supply its own supported rendering/observation
components where possible; shared preprocessing is acceptable if disclosed.
Empirical source/PSF templates require documented origins and template-level
ancestry isolation.

The original holdout varied each nuisance separately. New combinations may
already have occurred in randomized training. Specify whether a test setting
is a familiar combination, a new interpolation, or an extrapolation; do not
label all of them unseen conditions.

## Phase 3: freeze development and final evaluation

Start with a small development sample to debug the adapter and validate
physics. Keep it separate from final evaluation parents and templates.

A practical initial final design is 150 fresh independent parents, matched
across the selected domains and observation conditions. Choose the final
sample count using a stated precision goal and development estimates; 150
is a starting budget, not a guarantee of adequate power for every subgroup.
Keep the same physical proposal for A versus B. Any population-prior shift
gets a separate experiment, so it cannot be confused with a renderer effect.

Before final generation/scoring, freeze:

- Backend/environment versions and source/configuration hashes.
- Parent proposal, condition matrix, sample count, seeds, exclusion rules,
  and convention/quality gates.
- Checkpoints, normalization, inference, metrics, practical margin, bootstrap,
  and subgroup definitions.

Check new IDs, physical-state provenance, seeds, and template ancestry against
development data. Save target-free predictions and hashes before scoring.
Retain rejected cases and report failure counts by backend; do not quietly
score only systems both pipelines found easy. Report paired metrics on the
common valid set and coverage/failures on the full requested population.

## Phase 4: metrics and interpretation

For each domain and condition, compute the parent-paired difference:

```text
delta = MAE(randomized ensemble) - MAE(standard ensemble)
```

Negative values favor randomized training. The primary transfer estimand is
this difference in the predeclared alternate-domain stress composite, with
equal weights fixed before scoring. Bootstrap independent parents, retaining
all their conditions/backends together; use 10,000 resamples and a recorded
seed. Report seed-level results separately from the ensemble comparison.

Also report:

- Absolute MAE, bias, RMSE, P95 error, and fixed-threshold error fractions.
- Per-model A-to-B domain penalties.
- Change in the randomization benefit across A and B, using paired parents.
- Radius-bin and observation-quality outcomes, with subgroup counts.
- Failed renders, rejected inputs, runtime, and prediction failures.

Retain the earlier 0.01-arcsec practical margin if justified for the extension.
Freeze any support rule before evaluation. A proposed success criterion is
at least 0.01-arcsec improvement on the chosen alternate-domain stress
composite, a parent-bootstrap 95% interval wholly below zero, and an upper
canonical-degradation interval bound no larger than +0.01 arcsec.

If that rule fails, report the effect and uncertainty. Identify whether the
benefit disappeared, both models degraded similarly, or conventions/quality
checks remained unresolved. Agreement with a second package is not equivalent
to validated real-telescope accuracy.

## Training-effort control and later adaptation

The existing comparison uses 700 canonical versus 1,400 canonical-plus-varied
views. Before attributing improvement specifically to diversity, add a
canonical repeated-sampling run with an optimizer-update budget matched to
the randomized arm. Keep architecture, parent IDs, training seeds, optimizer,
and checkpoint-selection opportunities comparable, and log actual updates.
Predefine how early stopping and shape-bucket batches affect that budget.

Develop this control on validation data. Freeze new models before a new final
evaluation; do not select them against the original frozen holdout. Comparing
new models on target-domain data repeatedly turns that data into development
evidence and requires another independent confirmation set.

Training on the alternate simulator, mixing simulators, or fine-tuning on
target-domain examples can be a second study. Keep its target train/validation
and test partitions separate, and distinguish adaptation from zero-shot
generalization. A full train-on-A/train-on-B evaluation matrix is useful later
but is not required for the initial one-month extension.

## Why real observations need reference measurements

Real images can be processed and passed through the CNN. The current obstacle
is interpreting prediction accuracy, not executing inference.

In simulations, the generating `theta_E` is known exactly. For a real galaxy,
we do not have that generating input. We need an independently established
reference estimate, typically a reviewed lens-model result with uncertainty
and a documented target definition. A redshift or lens-candidate label alone
does not supply an Einstein radius. Image separation or arc radius may be a
proxy, but is not automatically the same SIE target.

For example, a CNN prediction of 1.10 arcsec cannot be assigned an error from
the image alone. If an independent compatible analysis reports 1.00 +/- 0.05
arcsec, the 0.10-arcsec difference is a residual against that uncertain
reference, not a known error against exact truth. Reference model assumptions
and shared-data/systematic dependencies must also be reported.

A useful real-data benchmark needs:

- Identified, reviewed galaxy-scale lenses with appropriate image products.
- Published or independently fitted radii, definitions, uncertainties, and
  fit-quality information; identify model-dependent reference measurements.
- Pixel scale, units, calibration, PSF, mask, and noise information sufficient
  for consistent processing and reference modeling.
- A fixed sample and scoring procedure, with all images of the same lens
  grouped together, and any reused templates excluded from test leakage.

Our CASTLES release has radius-related metadata and exploratory comparisons,
but these are not a governed, compatible accuracy benchmark for the frozen
CNN. Another telescope is useful only if these evaluation requirements can
be met; it does not solve the reference problem by itself.

Without reference radii, real images still support domain-coverage analysis,
failure screening, and prediction consistency across repeated observations.
Consistent predictions can all be biased, so stability is not accuracy.
Reference uncertainties require more careful analysis than treating every
catalog radius as exact ground truth.

## Proposed four-week execution

1. **Week 1:** resolve recorded runner verification issues; audit candidate
   backend, map conventions, and pass analytic/noiseless/noise controls.
2. **Week 2:** implement the release adapter and one additional domain shift;
   run development checks and the matched-training-effort control.
3. **Week 3:** freeze the selected models/protocol, generate new final parents,
   score once, and produce paired effects and failure summaries.
4. **Week 4:** write the transfer result and limits, package provenance, obtain
   review, and format for the selected workshop.

Time-box installation and convention work. If a full second stack is not
validated in time, publish the existing synthetic reliability result with a
stronger training-effort control and explicitly leave full cross-simulator
generalization open. Do not substitute an unvalidated renderer for a result.
